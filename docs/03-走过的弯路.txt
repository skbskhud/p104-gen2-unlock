
走过的弯路：已作废的结论与踩过的坑
=================

这篇文档记录本项目被推翻过的判断、差点踩中的陷阱、以及从中提炼的规则。
它对后来人的价值可能高于结论本身 —— 因为这些坑会重复出现。

每条都标明：当时的判断 → 实际是什么 → 怎么发现的 → 教训。

---

1. 已作废的结论账本
-----------

No.  曾经的结论  实际  怎么被推翻  教训
1  "全 4 KB 配置空间只有 Command 和 CacheLine 可写"  0x41C 可写，写入回读一致  直接写入并回读  阴性结论必须配对照写入；照搬旧结论会带错整条推理链
2  "VBIOS 的 DevInit 不写速率字段"  真反汇编发现 0x8C040 有 4 条写，且全在无条件路径上  从字节模式搜索升级为真反汇编  短字节模式搜索在 ROM 里必然误报，不能作为"不存在"的证据
3  "0x4B36 / 0x4B42 是写 0x8C040 的 DevInit 三元组"  它们是 condition[32]/[33]，是读不是写  逐指令解码  指令边界与操作类型必须解出来，不能只看地址出现
4  "0x8C040 不是速率请求，改它不能改链路速率"  写 SPEED 字段 + COMMIT 位实测把链路从 Gen1 改成了 Gen2  受控写入实验  "静态看起来不重要" ≠ "写它没用"
5  "LNKCAP 编码不自洽"（因为声明速率与当前速率不一致）  误读：LNKCAP 是能力声明，本来就不跟随当前链路速率  读 PCIe 规范  先分清"能力/声明"与"状态/当前值"
6  "找到了声明生成器的直接输入，输入空间已穷举"  被独立复核推翻：同值不同果  写同一个值在不同时间得到不同结果  存在未识别的状态变量（后查明是第 5 节的"状态 L"）
7  "LNKCTL2 是 Gen2 的开关"  它是温度计：L=0 时写 2 会被硬件钳回 1  连续 12 轮写入全部被钳回  相关 ≠ 因果；要区分"回显"与"输入"
8  "BAR0 0x118F78 是 PCIe 代际 strap"（曾被评为最高价值线索）  撤销：独立资料显示该地址在同类卡上读出来也是 0；本项目实测整片返回特权毒值  换一个独立来源交叉验证  单篇文档的叙述 ≠ 实测事实；高价值线索也要有第二来源
9  "XP3G 覆盖寄存器就是 Gen2 的使能位"（它们与 L=1 在 9 个状态里完美同步）  不是：对照实验证明即使写入它们、只要 0x8841C 的 bit15=0，L 仍为 0  单变量对照实验  同步 ≠ 因果：它们只是"总是和真正的使能位一起被写"
10  "0x1B87 是设备 ID 分支"（在驱动代码里看到它附近有分支）  实际是断言编号，不是按设备 ID 分支  反汇编确认  数字巧合；地址/常量必须结合上下文解码
11  "改设备 ID 就能让驱动把这张卡当 GTX 1070"  ① 文档写的改写路径在本芯片上运行期不可写；② 本机驱动的 INF 早就把 1B87 绑到 "GTX 1070" 那一段了 ⇒ 前提不成立  两条独立否证  先验证前提，再设计方案
12  "CMP 150HX 这个型号的解锁方法可以参考"  该型号不存在（转述讹误，CMP HX 系列没有 150HX）  查官方型号表  二手转述的型号/数字必须先核对一手来源
13  "PSTRAPS strap 寄存器里有 PCIe 宽度字段"（作为宽度解锁的最后软件希望）  没有：该寄存器文档化的 15 个字段全是 BAR 孔径/设备 ID/显存配置/ROM 类型/PCI 类别/晶振；覆盖机制的瞄准掩码对主机是毒值  读全文寄存器定义 + 用实测值反推字段  名字里带 "STRAP" 不等于有你想找的字段
14  "刷 GTX 1070 的 VBIOS 到这张卡上也许能拿到 Gen3"  静态对比：两份 VBIOS 在能力声明寄存器上的写入次数都是 0；动态实验：初始化那一刻请求 Gen3 也会被端点钳回  跨 SKU 对比 + 初始化时机实验  别为一个已被硬件拒绝的目标去刷固件（有变砖风险，收益为 0）

2. 深度案例：几次误报"Gen3 成功"
---------------------

这是本项目代价最大的教训 —— 同一个错误犯了三次。

2.1 第一次：用能力声明做速率判据

看到 LNKCAP2 从 0x02 变成 0x06，就宣布"Gen3 成功"（后来还出现过把 0x0E 当成"Gen3 能力值"的误判）。
实际：LNKCAP2 是声明支持哪些速率，可以在链路仍跑 Gen1 时保持 Gen2/Gen3 的值。

修正：速率判据只能用 LNKSTA[3:0]（当前速率）与带宽实测。

2.2 第二次：用短字节模式在 ROM 里"找到"代码

在 256 KB 的 VBIOS 里搜 3 字节模式，必然会随机命中。
曾把一段连续递增的计数器字节 0x0B, 0x0C, 0x0D, 0x0E 当成"Gen3 能力值 0x0E"。

修正：VBIOS 分析必须真反汇编；字节模式只能用于"缩小范围"，不能用于"证明存在/不存在"。

2.3 第三次：把"能写"当成"有效"

写某个寄存器成功落地（回读等于写入值），就认为它控制了声明。
实际：很多寄存器可写但不影响任何东西。

修正："写入落地"和"产生效果"是两件事，必须分别验证。

3. 数据污染类陷阱（这类最危险，因为它会伪造出"证据"）
-----------------------------

3.1 五份"对照 VBIOS"其实是 HTML 页面

为了做跨 SKU 的 VBIOS 对比，本地下载了 5 份"对照 VBIOS"。
第一次扫描"P104 的 VBIOS 里有没有写某个寄存器"——全部 0 命中，看起来是漂亮的阴性结论。

★ 发现问题的办法是阳性对照：同一套扫描逻辑对 P104 自己的 VBIOS 也应命中 0x08C040（已知它写过），
结果阳性对照也是 0 命中 ⇒ 说明扫描对象本身有问题，不是结论有效。

一查：那 5 个文件是 HTML 下载页面（404/登录页），根本不是 ROM。

修正：
1. 任何扫描都必须先跑阳性对照；
2. 检查文件头（ROM 通常以 0x55AA 结尾、有 NVIDIA 标志），不要只看文件名。

3.2 转储文件里的"填充值"被当成真实寄存器

BAR0 全量 dump 里，读失败的地址会被工具写入填充值：

0xDEADBEEF / 0xDEADDEAD   ← 转储工具自己写的标记
0xBADF5040 / 0xBADF1100   ← 硬件返回的特权毒值
0xFFFFFFFF                 ← 映射完全失效

一次跨两份 dump 的 diff 得出"复位改变了 266,151 个寄存器"的结论 ——
其中 265,984 个是填充值之间的差异（两份 dump 用了不同的填充约定），真实差异只有 167 个。

修正：
1. 哨兵值要按族处理（任何 0xBAD????? 一律视为"不可访问"），不要逐个列清单；
2. 跨 dump 对比前先确认两边的读失败约定一致；
3. 报告 diff 结果时必须同时给出"原始差异数 / 剔除哨兵后的真实差异数"。

3.3 写通道 IOCTL 用错一个数字 → 一整批"寄存器只读"结论

早期用某个内核驱动的 IOCTL 写寄存器，用了 0x9C406148，实际应为 0x9C40A148。
写全部静默失败 ⇒ 得到一整批"这些寄存器是只读的"结论，全部是假的。

修正：写通道必须先自检 —— 找一个已知可写的寄存器（如 Command 寄存器），
写入、回读、确认值真的变了，然后才开始做"写不进去"的实验。

3.4 假阴性：只等 3 毫秒 + 用 XOR 探测

早期的一个"哪些寄存器可写"的扫描：每个候选写一次、等 3 ms、用 XOR 判断变化。
把实际可写的寄存器判成了只读。

修正：写-读之间要给足 settle 时间；判据用"回读是否等于写入值"，不要用 XOR 差值的间接推断。

3.5 熔丝写入测试：第一次结论作废

第一次测"熔丝能不能被主机覆盖"，结论是"不能"。
但复核时发现：那一轮里连"对照写入"也失败了 —— 也就是说那一次整个写通道都不通，
所以"熔丝写不进"这个结论没有证据支持。

修正后重做：每次探测都配一次必须成功的对照写入（写一个已知可写位并回读），
对照通过后才采信"目标写不进"。

⇒ 这条后来成了本项目的铁律：阴性结论必须配对照。

5. 方法学教训（可直接迁移到别的逆向项目）
----------------------

1. 判据只能用"当前状态"，不能用"能力声明"。
2. 阴性结论必须配对照写入：证明"写不进"之前，先证明"同一时刻别的地方写得进"。
3. 写通道必须先自检：写入 → 回读 → 值真的变了，才算通道可用。
4. 任何扫描先跑阳性对照：如果阳性对照都不命中，问题在扫描器/输入，不在被测对象。
5. 穷举 > 抽样，且穷举必须记录并控制基线状态。
6. 相关 ≠ 因果：多问一句"它是回显还是输入？"（温度计 vs 开关）。
7. 同步 ≠ 因果：两个寄存器在多个状态里一起变化，可能只是"总是被同一次操作一起写"。
   判别方法：单变量对照。
8. 同值不同果是隐藏变量的报警器：同一个写操作结果不同 ⇒ 一定有未识别的状态。
9. 主动交代覆盖边界："没找到"和"扫过了"是两句话；给出覆盖率而不是给结论。
10. 单篇文档的叙述不等于实测事实：高价值线索也要有第二来源（本项目因此撤销过一条最高价值线索）。
11. 先验证前提再设计方案：例如"改设备 ID"的前提是"驱动没把这张卡当目标卡"，
    而这个前提是假的。
12. 给结论标强度：实测 / 强支持 / 推测 / 未验证 / 已否证 —— 不允许混着说。
13. 不要为一个已被硬件拒绝的目标去承担不可逆风险（刷固件、动烙铁）。

6. 本项目自己撤销或降级的判断（诚实记录）
----------------------

判断  处理  原因
0x118F78 是 PCIe 代际 strap（曾被列为最值得做的线索）  撤销  独立来源显示该地址在同类卡上读出 0；本卡实测整片返回毒值
"状态 L 可以用 LNKCTL2 观测并控制"  降级：只能观测，不能控制  写 LNKCTL2=2 在 L=0 时被硬件钳回 1
"PSTRAPS 可能是宽度解锁的最后软件入口"（曾列入线索清单）  撤销  该寄存器没有宽度字段，覆盖机制不可瞄准
"全 BAR0 都已扫描"  改为"扫描了设备向主机开放的 23.5% 的 dword（整页口径 1.9%）"  覆盖率统计
"Gen3 已穷举式证明不可达"（强版本）  降级为"在所有已知主机可写入口上被拒绝，且有正面机制解释"  独立复核指出文档覆盖不足（某区块文档覆盖仅 0.3%）
