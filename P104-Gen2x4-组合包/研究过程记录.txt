一、问题是什么
-------

一张 NVIDIA P104-100（GP104，和 GTX 1070 同核心），插在 CPU 直连的 PCIe x16 槽上，
链路只协商到 PCIe 1.1 x4（2.5GT/s × 4）。

LNKCAP  = 0x00463C41   → 声称最高 2.5GT/s，最高 x4
LNKSTA  = 0x00001041   → 当前 2.5GT/s x4
实测带宽 H2D 0.780 GB/s / D2H 0.851 GB/s

而它的上游根端口是 Gen4 x16（00:01.0，8086:9A01，LNKCAP2 = 0x0180001E，
声明支持 2.5/5/8/16 GT/s 全部速率）。平台侧完全没有瓶颈，卡却只跑 1/8 的速率。

目标：把链路速率提上去。宽度（x4）已经受物理限制，不动。

---

二、第一阶段：所有"权威结论"都指向"硬件锁死"
------------------------

社区共识（LTT 论坛、P104/P106 魔改圈）是：

"lane 和世代限制是硬件限制，不是软件能解开的。
这颗芯片是低规格分档（binned lower），本身就不支持 Gen3 或超过 4 条 lane。"
"是 PCB 限制，那些 lane 拿不回来。"

同一台机器上做的实验也支持这个结论：

层面  做法  结果
配置空间  写 LNKCAP / LCAP2 / TLS  读回原值；TLS 被"钳回"1
GPU 内部寄存器（MMIO）  写 0x880A4(LCAP2)=0x06、0x88084 速率位、0x880A8(TLS)=2  全部被"忽略"
驱动策略  RmForceEnableGen2=1 + 重启设备  nvidia-smi 的 gen.max 变成 2，但链路仍是 Gen1
VBIOS  解析 ROM 里的 PCIe 初始化表  表里只写 0x88088 和 0x8C040；能力类寄存器地址在整个 262KB ROM 里出现 0 次
熔断位  按 170HX 社区的熔断地址表读取  全部读回特权哨兵 0xBADF1100，无法判定

结论写成："P104-100 的 PCIe 只能 Gen1，是它上电时的板级/芯片级配置（strap）决定的；
配置空间、GPU 内部寄存器、驱动策略、VBIOS 四个层面都试过了——全都改不动。"

这个结论看起来无懈可击。但它有一个致命的隐藏前提。

---

三、★ 转折点：发现自己一直在用坏掉的工具测量
-----------------------

接手后，我做的第一件事不是继续实验，而是检查测量工具本身。

翻前一轮留下的探测脚本，在第 43-49 行看到一段注释：

CTL_CODE(DeviceType, Function, Method, Access)
==============================================

= (DeviceType << 16) | (Access << 14) | (Function << 2) | Method
================================================================

之前漏了 Access 位，导致 DeviceIoControl 返回 ERROR_INVALID_FUNCTION(1)。
==============================================================

CTL_WRITE_CANDIDATES = [(OLS_TYPE << 16) | (acc << 14) | (0x852 << 2) for acc in (2, 1, 0, 3)]

这段注释把答案写对了。 但同一个文件里实际执行写入的函数硬编码了错值：

kernel32.DeviceIoControl(h, 0x9C406148, ...)   # 错！写请求从未下发

而它的自检函数只判断"IOCTL 是否被接受"，不校验"寄存器值是否真的改变"，
所以产生了假阳性——自检报告"找到可用的写 IOCTL"，实际上一次都没写进去。

这个发现意味着什么

前一轮所有"寄存器只读""写不进去""被钳回"的结论，全部是测量工具故障的投影，
不是硬件事实。

正确的写 IOCTL 是（运行时自检出来的）：

读: 0x9C406144   （本来就对）
写: 0x9C40A148   ★ 不是 0x9C406148

修正后立刻做的对照验证

在相信任何测量之前，先用一个已知可写、且不承担关键功能的位做对照：

目标  寄存器  写入前  写入后回读  判定
P104 01:00.0  COMMAND 0x04  0x00100006  0x00100106  可写 ✓
P104 01:00.0  LNKCTL[1:0]  0x10410140  0x10410141  可写 ✓
根端口 00:01.0  LNKCTL[1:0]  0x30410040  0x30410041  可写 ✓
根端口 00:01.0  LNKCTL2 TLS  0x00010001  0x00010002  可写 ✓

"根端口只读""TLS 写不进"这些结论当场作废。

### 💡 教训一
在相信任何测量之前，先证明你的测量工具是好的。
用一个已知可写、且不影响关键功能的位做对照。
这次如果没做这一步，后面所有努力都会建立在假数据上。

四、第二阶段：把"只读"的假象一个个推翻
--------------------

写通道修好后，重新做了一遍"只读"测试。结果确实有一部分是真的只读：

路径  具体操作  结果
配置空间 LNKCAP2  写 0x06/0x0E/0x00  回读恒为 0x00000002 ❌ 真只读
配置空间 LNKCTL2  写 TLS=2  回读恒为 0x00000001 ❌ 真只读
BAR0 0x880A4（LCAP2 镜像）  写 0x06  回读 0x00000002 ❌ 真只读
BAR0 0x880A8（LNKCTL2 镜像）  写 0x02  回读 0x00000001 ❌ 真只读
BAR0 0x88084（LNKCAP 镜像）  写 0x00463C42  回读 0x00463C41 ❌ 真只读
BAR0 0x8C040（速率请求）  置 SPEED=1 + COMMIT  SPEED 可写；bit0(COMMIT) 被硬件自清 ✅ 部分可写
根端口 LNKCTL2  写 TLS=2  0x00010001 → 0x00010002 ✅ 可写

所以真相是分层的：外围寄存器可写，"声明"类寄存器确实写不动。
但这次我们知道哪些是真的写不动，而不是被坏工具骗。

一个反直觉的发现

卡内部其实一直在请求 Gen2：

BAR0 0x8C040 = 0x20045800  →  SPEED[19:18] = 1 = 5.0GT/s（Pascal 编码）

卡自己在要 Gen2，但它的"声明"只到 2.5GT/s。
而链路速率取两端能力的较小值 —— 所以声明不改，一切白搭。

关于"watchdog"的一个真相

前一轮记录里有一句很有名的话：

"驱动会毫秒级把 LINK_CONFIG_0 改回 Gen1，必须常驻 watchdog 对写。
实测 1-2 分钟内检查 1910 次 / 补写 1910 次。"

我当时实测了漂移率（20 秒读 397 次）：

读取 397 次，发现需要补写 397 次（比例 100%）
观察到的值分布: 0x20045800: 397      ← 397 次读到的值完全相同

397 次读到的值一模一样，而且 bit0(COMMIT) = 0。

watchdog 的判据是 SPEED != 目标 || bit0 == 0。而 COMMIT 位会被硬件立即自清，
bit0 永远是 0 → 每一轮都必然判定"需要补写"。

⇒ 那个 1910/1910 的 1:1 比例，是 COMMIT 自清造成的，不是"驱动在回写"。
前一轮把因果理解错了（当时没有做 A/B 对照）。

### 💡 教训二
1:1 的计数不能当作"有竞争"的证据。 先做 A/B（停掉 watchdog 看值会不会变）。

---

五、第三阶段：定位到"声明"这一层
-----------------

既然请求值可写、声明写不动，那唯一的希望就是：让"声明"被重新计算一次。

"声明"（LNKCAP / LNKCAP2）是 PCIe 核在设备初始化时算出来并锁存的。
所以思路变成：触发一次设备重新初始化。

于是把当时能想到的复位手段全试了一遍：

复位方式  结果
PCIe FLR（Function Level Reset）  ❌ DEVCAP bit28 = 0，卡不支持
D0 → D3hot → D0（写 PMCSR）  ❌ 设备正常回来，声明不变
pnputil /restart-device  ❌ 命令成功、卡没掉，声明不变
完整重放前一轮 MMIO 配方 + 复位  ❌ 使能位全部写入成功，声明不变
Disable-PnpDevice → Enable-PnpDevice  ✅ 声明变成 0x00000006！

最后一条就是答案。 但当时我还没试它——我把它和前四条归为一类，
以为"设备复位"都是一回事。

### 💡 教训三
"复位"不是一个动作，是一族动作。 它们的深度不同：
· pnputil /restart-device → 只重启驱动栈，设备不离开总线
· Disable → Enable（SetupAPI DIF_PROPERTYCHANGE）→ 设备真的从总线上摘下来再装回去

---

六、第四阶段：为什么 x1 口能成、x16 口不能（一次错误的判断）
----------------------------------

期间有一个重要的事实：同一张卡插在 x1 延长线上（PCH 的 00:1D.3 口）时，
上一轮的 Gen2 破解是成功的（带宽 0.197 → 0.393 GB/s，LCAP2 变成 0x06）。

我当时的推理是：

· x1 口是 PCH 侧端口 → 策略宽松 → 能出 Gen2
· x16 口是 CPU PEG 端口 → 被固件钉在 Gen1 → 出不来
· 证据：同一颗 CPU 的另一个 PEG 口（00:06.0）在跑 Gen3 x4，
  而 00:01.0 只能 Gen1 → 说明是逐端口的策略

这个推理看起来证据充分，但结论是错的。

因为我漏了一个关键算法：x1 口上那次成功，恰好包含了"禁用→启用"这个步骤
（实测量的操作流程就是"先禁用显卡再启用显卡，然后破解"），
而 x16 口上，我从来没做过这一步。

对比表：

环节  x1 口（成功）  x16 口（我当时的做法）
写使能位 + 速率请求  ✅  ✅
禁用 → 启用  ✅（实测含此步）  ❌ 只做了 pnputil /restart-device
两端 TLS + 重训  ✅  ✅
结果  Gen2 成功  Gen1（声明不变）

⇒ 不是端口被封，而是"重新锁存声明的时机"没有被触发。

### 💡 教训四
当两次实验结论矛盾时，先怀疑"两次实验的操作步骤不完全一样"，
而不是急着构造一个解释现象的物理模型。
我当时构造了"端口策略钉死"这个模型，它解释了所有现象，
但真相要简单得多——少做了一步。

奥卡姆剃刀：能解释现象的最简假设，通常比精巧的假设更接近真相。

---

七、★★★ 最终突破：真正的"禁用→启用"
---------------------

线索来自两条独立的社区经验

线索 A：CMP 40HX 解锁项目的 README

40HXUnlock v3.2.0 的策略表里有一条：

Gen2PnpFallback = 1（默认开）
失败保底（v3.1.1+）：不依赖 Stage2 —— Stage1 重训失败即自动
禁用→启用 40HX（DEV_1F0B） 完整重载 nvlddmkm
（驱动重读 RMPcieLinkSpeed 等策略 + 整卡复位）再解锁一轮

同一份 README 还提到，实测观察到的现象是"破解第一次失败，再破解一次就可以了"——
而这个"第二次"正是 Gen2PnpFallback 自动做的禁用→启用。

线索 B：实测经验

"先禁用显卡，再启用显卡，然后破解第一次会失败，再破解一次就可以了"

两条线索指向同一个环节。

实测：一步到位

第 1 步  写使能位 + 速率请求
         0x8841C: 置 bit11/13，清 bit12/14
         0x88610: 清 bit12，置 bit0
         0x8872C = 6
         0x8E110/0x8E11C/0x8E120/0x8E12C = 1 / 4 / 0 / 0x00200000
         0x8C040: SPEED[19:18] = 1 (5.0GT/s) + bit0 (COMMIT)

第 2 步  ★★ 禁用 P104 → 等它从总线消失 → 启用 → 等它回来
         （SetupAPI: DIGCF_PRESENT + DIF_PROPERTYCHANGE + DICS_DISABLE/DICS_ENABLE）

         ⇒ 复位后立刻：LNKCAP=0x00463C42(Gen2 x4)
                        LNKCAP2=0x00000006   ← 声明解锁了！
                        TLS=2

第 3 步  两端 TLS=2 + root/GPU 交替重训
         ⇒ 一轮就上：LNKSTA=0x00001042 (5.0GT/s x4)

第 4 步  常驻按住循环（每 20ms 重写使能位 + 速率请求 + 两端 TLS）
         ⇒ 保持率 100%

结果

H2D  0.780 → 1.553 GB/s   （1.99×）
D2H  0.851 → 1.693 GB/s   （1.99×）

第 4 步为什么不可省

实测：一旦停止按住循环，链路立刻掉回 Gen1（LNKSTA 从 0x00001042 变回 0x00001041），
带宽也回到 0.78 GB/s。

这不是 bug——这正是 40HX 工具需要 watchdog / 常驻守护 的原因。
NVIDIA 驱动会持续把链路策略往回压，必须有一个常驻进程和它对写。

顺带必须处理的两个坑

1. 驱动策略 RMPcieLinkSpeed 必须 = 1。
   =2 会把 GPU 的 LNKCTL2 TLS 钳死在 Gen1
   （症状：写 TLS=2 回读仍 1、重训全败）。工具在解锁前会预检并自动改正。

2. 设备实例必须只认 Present = True 的那个。
   设备换过插槽后，Windows 会留下"幽灵"记录（Present = False）。
   如果枚举时抓错（或者把多个实例拼在一起），Disable-PnpDevice 会直接报错失效。
   本工具用 DIGCF_PRESENT 过滤 + 只取第一个。

九、思维方法总结：这次真正起作用的几条原则
---------------------

1. 先验证测量工具，再相信测量结果 ⭐ 最重要

前一轮花了大量时间得出"硬件锁死"的结论，全部建立在写通道损坏的工具上。
修好工具后，一半的"只读"结论立刻蒸发。

做法：任何寄存器/内存实验开始前，先写一个已知可写、且不影响关键功能的位，
回读确认。这一步花 2 分钟，能省掉几天。

2. 结论要标注"证据强度"

整个项目里我把结论分成三类，从不混用：

· 已实测确证（有原始寄存器读数 + 带宽数字）
· 推测（能解释现象，但没直接证据）
· 未验证

这样做的价值：当我发现"端口策略钉死"这个结论其实建立在"少做了一步"之上时，
能立刻定位到是哪一层出了问题——因为我把"推测"和"确证"分开了。

3. 两次实验矛盾时，先查操作步骤差异，不要急着建模型

x1 成功 / x16 失败，我第一反应是构造"端口策略不同"的模型（还找了旁证：
另一个 PEG 口跑 Gen3）。真相简单得多：x16 时少做了"禁用→启用"这一步。

奥卡姆剃刀：先排除"我操作不一样"，再考虑"硬件不一样"。

4. 反直觉的测量结果，往往指向真正的机理

· 0x8C040 的 COMMIT 位每轮都被自清 → 说明看门狗那套"1:1 计数"是假象
· 卡内部在请求 Gen2，但声明只到 Gen1 → 说明瓶颈在"声明"而非"请求"
· x1 口上声明会变、x16 口上不变 → 说明声明不是恒定的，而是可被重新锁存的

每一条都直接改变了搜索方向。

5. 借鉴成熟项目的"操作经验"，而不只是"技术细节"

40HX 项目的 README 里那句 Gen2PnpFallback 说明，是纯文字的操作描述，
没有任何寄存器细节 —— 但它是整件事的钥匙。

同族硬件的民间经验文档（尤其是"失败排查"章节）价值极高，
因为它们记录了"什么操作顺序能成功"这类无法从寄存器手册推出的知识。

6. 每一步都要可还原、可复现

所有脚本都：写入前备份、失败逐项还原、每步回读验证、结果落 JSON 存档。
这让"哪一步真正起了作用"能被精确定位。

十、走过的弯路清单（写给后来者）
----------------

直接跳过这些，能省几天：

No.  弯路  为什么错  正确做法
1  相信"寄存器只读"  写通道坏（IOCTL 错值 + 自检不校验值）  先做写通道对照自检
2  把 1910/1910 当成"驱动在回写"  是 COMMIT 位自清导致的必然判定  做 A/B：停掉循环看值变不变
3  用 pnputil /restart-device 当"整卡复位"  设备不离开总线，复位深度不够  必须 Disable → Enable
4  构造"端口被固件钉死"的模型  其实只是少做了一步  先对比两次实验的操作步骤
5  在 x16 口上纠结端口策略  端口本来就没问题（LNKCAP2 声明支持全速率）  先触发声明重锁存
6  想靠 D3hot→D0 重跑 DevInit  D3hot 不重跑 VBIOS，且不重锁存声明  用 SetupAPI 整卡复位
7  指望 FLR  P104 的 DEVCAP bit28 = 0，不支持  同上
8  追查编解码器（NVENC/NVDEC）  P104 的编码器硬件不存在（四条独立证据）  不要做
9  用 nvflash 刷 VBIOS  实测会导致机器重启；且 ROM 里没有能力字段  用 CH341A 编程器（如确需）
10  枚举设备实例时不区分幽灵记录  Present=False 的实例会导致禁用失败  用 DIGCF_PRESENT 过滤
